# 完整提示词的质量放行

本文件是**全套路径**的放行流程。默认的轻量路径不走这套：它只运行 `check_prompt.py`，六域审查、用户锁和逐镜摄影都在头脑里核对完，不建 requirements.json、不写 review.json、不派独立复核、不跑 verify_delivery。全套只在两个条件下触发（用户要求严格审、事先约定的审核节点），分法见 SKILL.md「流程分级」；复杂稿不自动触发，第一版也不触发，默认同样走轻量路径。

用于全套路径的新稿、完整操作命令和修订。走全套时每次成稿都执行适用检查；“自检”只改变报告展示，不决定是否做必要检查。概念草案按用户所要的阶段交付，不冒充已验收成稿。

## 执行顺序

1. **来源与需求核对**：先保存原始请求和有效补充，再建立 requirements.json。逐字锁来自原请求或实际父稿，语义锁另列；修订先核对修订范围与真实父稿，将用户认可的成功项及其原话、版本纳入现有需求；只有超出已授权范围的实质取舍才需用户决定。读取实际素材，记录职责；不可读、身份未知、来源不明不能猜为事实。普通未锁定设计自主完成。
2. **适用设计**：读取相关经验、案例与全部适用工艺卡，按入口设计每镜。记目标观感、关键事件、起终状态、摄影与空间关系、适用的表演/受力/特效，不为填表添加人物天气。所选设计必须落成可见句。摄影按 SKILL.md 的本用户偏好，逐镜填写下文 camera；发生同音替换时保留下文 pronunciation 映射。
3. **完整成文**：用户要求、采用设计、摄影幅度与结果都在正文里落实，不停在设计记录上。
4. **专业审查与修复**：核对来源到需求、需求与设计到正文，以及六域之间的关系；同时检查重要效果是否丢失或减弱，以及是否新增无必要的微观安排或冲突，等义合并与成功项保护按 revise-rules.md 第 7、11 节，不新增审查轮次。六域均判定适用性；适用域必须引用本版正文并解释关系，不适用必须有原请求/父稿事实依据。检查画幅能否看见事件、相机能否同时执行、动作/对白是否装得进时长、受力和跨镜因果是否连续。动作容量：平均每拍 ≥0.5 秒是用户实测得到的经验线索（L064），不是通过保证——用户多次实测里模型多会以加速方式完成密动作，0.5 秒一个动作可完成，1 秒里塞 2 到 3 个不同动作离谱。它可作为"不因密度自动拆镜"的依据，仍要按动作依赖与可读性判断：加速可能牺牲可读性或漏动作，真正需要看清的动作单独给时间。check_prompt 在平均 ≤0.5 秒/拍（每秒 2 拍以上）时提醒，该提醒照常逐条裁定。对白按真实说话时间算。只有“高级感”“很激烈”或只有关键词不能通过。先运行 `check_prompt.py --report ~/.aigc-video-gate/<时间戳>.json`（`--report` 每次换一个新路径，Stop 钩子按它核对本轮交付；没有报告的完整稿钩子会代跑一遍机械检查），保存检查结果及合成完整稿；逐项核对需求与本版正文，处理所有警告。自己造成的问题先内部修复再查，不增加用户确认轮次。
5. **必要独立复核**：只在全套路径做（用户要求严格审、或事先约定了审核节点；复杂度本身不触发），在作者之外的**新上下文**复核：Claude Code 用真实新上下文的 Agent 子代理，Codex 开新会话或独立子任务；只给它原始要求、素材职责、父稿、最终稿和 qa-checklist.md，不给作者的审查结论、理由或“已通过”口径。**完整复核只做一次**，不做第二次全量复核。

   **修复后的闭环（必须走，否则第 6 步的哈希核对必然失败）**：一次完整独立复核之后，作者按复核意见修复；修完**不是**自己写一份新记录，而是把改动点（diff，或改动涉及的整镜）交回**同一个复核者**，请它只核验修复点及其关联影响（相邻镜头、被改动牵连的依赖），不重做全量审查；复核者据此出具**绑定最终正文哈希**的新 independent.json（prompt_sha256 = 最终交付那一版的 checked_sha256，context 与第一次相同，saw_author_review 仍为 false）。Claude Code 用 `SendMessage` 续用同一个子代理（同一 Agent，上下文保留），Codex 在同一会话里继续。**作者不得自己改写复核记录的哈希或结论**——手改 independent.json 的 prompt_sha256 让它对上正文，等同伪造独立复核。若修复后复核者不可达，说明情况并按无法补齐的必要缺项处理，不放行成"已验收成稿"。

   **核验修复时的报告范围（收紧）**：只有两类问题写进 `unresolved`——**① 修复点没修好；② 修复引入了新的矛盾**。复核者这一轮新看到的其它意见（第一次复核没提、与本次修复无关的改进点）写进 `suggestions` 数组，每条 `{"point": "在哪一镜哪一句", "suggestion": "建议怎么改", "reason": "为什么"}`；`suggestions` **不进 unresolved、不阻断放行**，verify_delivery 不读它，作者按需采纳或说明不改。不要用"顺手又发现几条"把放行拖成第二次全量复核。
6. **最终检查与导出**：运行 verify_delivery.py，带 `--output`、`--report`（写到 `~/.aigc-video-gate/`）和 `--response`。轻量路径没有这一步，它的对应物是第 4 步那次 `check_prompt.py --report`。检查对象必须是实际要交付的那一版；正文、需求、采用设计或父稿改过就重跑，复杂任务的旧独立复核不能覆盖修改后的版本——本轮用户消息之前生成的报告不算本轮验收。
7. **交付导出的正文**：ready=true 后交付 `--response` 生成的成品。提示词正文及生成回执原样取自 response 文件。允许在代码块外写必要表头、问题、例外和变更摘要；这些说明不得混入可复制提示词。用户只要提示词时加 `--response-mode prompt-only`，省略外部说明，成品只有代码块、不带交付行，内部检查不变。

**交付约定**：成品一律用 ` ```text ` 代码块；引用旧稿用 ` ```quote `，概念草案用 ` ```draft `，工具输出用 ` ```json ` / ` ```bash ` / ` ```diff `。代码块**内**只放成品正文，逐字来自 response 文件；表头（锁定 / 待你定 / 升级 / 翻译）、例外说明、变更摘要、"待你定：这镜是否固定"这类问题写在代码块**外**，不受"原样粘贴"限制。裸文本贴出来的完整稿、局部镜头、操作命令一样按提示词核对。

**放行条件（全套路径）**：检查器未执行、执行失败、版本不符、专业问题未解决、那一次必要独立复核未完成时，不能标成已验收成稿。轻量路径的放行条件是 check_prompt 无错误、警告已逐条裁定、作者核对完成。自己造成的问题先内部修复，复查受影响依赖后重新放行，不把每个修复都交给用户批准。无法补齐的必要缺项明确说明；用户仍要拿到草稿时标为待验证候选，不用"草案"标签偷偷降级用户要求的完整成稿。

可选宿主钩子另见 `../../hooks/README.md`；本体流程与验收不依赖钩子。

内部记录不进入视频提示词。用户只要提示词时可省略展示回执，必要检查仍完成。长度以能追查判断为准；禁止用“已检查”“合理”代替具体依据。

## 工作文件和接口

每个候选版本使用独立工作目录：原始请求/需求、正文、审查记录、原始运行结果。父稿单独保留。不要把已有交付路径用作临时文件。

requirements.json 在写稿前建立，字段如下（JSON 是内部数据）：

```json
{
  "request": "原始用户请求与有效补充原文",
  "task": "生成",
  "labels": [],
  "assets": [],
  "total": 8,
  "untimed": false,
  "exact_locks": ["原请求或父稿里的逐字文字"],
  "requirements": [
    {"id": "R1", "source": "本次原请求或父稿的准确引文", "text": "这条要求的具体含义"}
  ],
  "complex": false,
  "complexity_reason": "按 SKILL.md 流程分级判断本次是否需要独立复核：只有用户要求严格审或事先约定了审核节点才 complex=true，稿子复杂或是第一版都不算"
}
```

- labels 按真实上传顺序，无素材明确写 []；写 `图1` 或旧写法 `图片1` 都行，脚本会归一成 `图N / 视频N / 音频N` 再与正文核对。assets 每份一条 `{ "label": "图1", "status": "read", "role": "只负责衣服", "evidence": "实际读取记录与相关可见事实" }`；读不到标 missing，不能放行。
- 精确文字用 exact_locks，新稿无需伪造父稿。语义要求须进入 requirements，不能把故事、动作、结果只留在原始请求里不核对。锁定列表由原请求建立，不从成稿倒推。**source 只能引本次对话的原请求、有效补充或真实父稿**：持久记忆、旧项目文件、以前会话里的设定不能当 requirement 的 source，除非用户在本次对话里确认过（那就引用用户本次确认的那句话）；没确认的设定留在表头"待你定"行，不进 requirements、不进 exact_locks。
- 修订时提供真实 --baseline；可用 unchanged 数组，如 `[1,3]`。局部段用 --partial，review 的 quote 与哈希对应放回父稿后的完整稿。
- 用户明确无时码或 UI 控时长时 untimed=true，仍由专业审查判断动作/对白容量；未写时码不自动意味着偷省检查。
- 自写否定默认 0 条预算（固定句不计；五段 / 六段旧壳的修订仍按结尾段 4 条预算）；逐字用户锁保留且不占预算。每条自写否定都是一条待裁定提醒，确认必要的写进 requirements 的 negative_exception 数组：

```json
"negative_exception": [
  {"sentence": "不出现现代物品。", "reason": "古装外景里群演常带手表和塑料瓶，正向写服装道具管不到画面边缘，没有等价正向写法"}
]
```

每条的 sentence 必须与稿里那句**镜内否定句整句一致**（旧壳稿是结尾段里一条独立否定条款）；同一句重复声明、只截一个片段都不计数——四段稿点名了却在稿里找不到会直接报错，旧壳稿的条数要覆盖超出 4 条预算的部分。verify_delivery 会先查重（重复句子直接报错），再把去重后的句子用 `--negative-exception` 传给 check_prompt 逐句核对。reason 写防什么、为什么没有等价正向写法；“质量需要”“需要”“必要”这类空话和过短的理由脚本会直接拦下——但脚本只能查长度与空话，必要性仍由专业审查判断。审查记录仍须裁定相应提醒；无据的禁止项不放行。

review.json 由真实检查产生：

```json
{
  "prompt_sha256": "check_prompt 输出的 checked_sha256",
  "requirements_sha256": "requirements.json 文件原文的 SHA-256",
  "baseline_sha256": null,
  "author": "实际作者标识",
  "reviewer": "实际审查者标识；普通自审可与作者相同",
  "coverage": [
    {"id": "R1", "status": "pass", "quote": "最终完整正文中准确存在的一段", "reason": "这段怎样兑现原要求"}
  ],
  "checks": [
    {"id": "intent_assets", "status": "pass", "quote": "最终正文原句", "reason": "意图和素材职责是否成立"},
    {"id": "composition_camera", "status": "pass", "quote": "最终正文原句", "reason": "需要看到的事如何被镜头拍到"},
    {"id": "action_performance", "status": "pass", "quote": "最终正文原句", "reason": "动作因果与表演是否成立"},
    {"id": "timing_continuity", "status": "pass", "quote": "最终正文原句", "reason": "容量与起终状态是否成立"},
    {"id": "materials_light_vfx", "status": "pass", "quote": "最终正文原句", "reason": "材料、光和特效关系是否成立"},
    {"id": "sound_delivery", "status": "pass", "quote": "最终正文原句", "reason": "声音、逐字台词、最终交付约束是否成立"}
  ],
  "camera": [
    {"id": 1, "mode": "moving", "quote": "本镜实际运镜原句", "effect_quote": "本镜可见幅度或画面变化原句", "reason": "实际路径、幅度与可读性判断；其余镜头各增一行"}
  ],
  "warnings": [],
  "unresolved": []
}
```

- 六域不得漏项，不适用使用 `{ "id": "...", "status": "na", "source": "原请求/父稿准确引文", "reason": "为什么不适用" }`。有问题记 fail/unknown，不能删掉该域让校验通过。
- coverage 必须覆盖每条需求 id；每个通过项要有正文原句和实际理由。复杂镜头组在 reason 中明确镜号、作用关系和相邻依赖，不能只引用一条结尾句代表全片已审。
- warnings 必须逐字对应本次 checker.warnings。每条使用 `{ "message": "警告原文", "decision": "false_positive 或 accepted_constraint", "quote": "正文/请求依据", "reason": "为什么它不构成未解决问题" }`。真问题先修复重跑；不能用“已修复”消掉仍存在的警告。没有素材时，对未提供 --labels 的提醒可据原请求与实际无素材集合裁定。
- camera 的 mode 只能是 moving / fixed / preserved，各自必填字段见下文「摄影」小节；作者自行固定（旧的 fixed_by_design）**已撤销**，脚本遇到直接报错。
- baseline_sha256 在有父稿时填父稿文件原文 SHA-256，无父稿为 null。需求哈希必须取文件真实文本，不能对重新序列化后的对象取哈希。

复杂任务的 independent.json 最少包含：prompt_sha256、requirements_sha256、reviewer（实际独立审查者且不同于 author）、status（pass/fail/unknown）、quote（本版正文引文）、reason（具体审查发现与结论）、unresolved（问题数组），以及 context——记清楚这次复核是在哪个新上下文做的。可选 `suggestions`（核验修复那一轮的新发现，见第 5 步）：verify_delivery 只读上面这些必填字段，多出来的 suggestions 不影响放行。

```json
"context": {"kind": "subagent", "id": "Agent 子代理 independent-review-2026-09-20T21:05", "saw_author_review": false}
```

kind 只能是 subagent（Claude Code 的 Agent 子代理）、new_session（Codex 新会话或独立子任务）或 other_person（另一个真人）；id 要能事后定位到那个代理或会话；saw_author_review 必须是 false，即复核者没读过作者的审查结论。
同一上下文里换个名字不算独立；主审读完作者的全部过程和结论、再另存一份“独立结论”也不算。身份声明不是身份证明，应保留对应工具/上下文记录；作者不能自己换名补一个假独立结果。

```sh
python3 scripts/verify_delivery.py --prompt prompt.txt --requirements requirements.json --review review.json \
  --report ~/.aigc-video-gate/2026-09-20T210500.json --output delivered.txt --response response.md
```

修订增加 `--baseline parent.txt`，局部镜头增加 `--partial`；复杂任务增加 `--independent-review independent.json`。用户只要受影响镜头时再加 `--output-scope affected`：仍审查合成完整稿，只导出本次受影响的完整镜头；其 delivered_sha256 与完整 checked_sha256 分别保存。`--response` 只在 ready=true 且写出了 `--output` 时生成，内容是拼好的成品：一个 text 代码块装着正文，下面一行“交付校验通过（正文 xx｜需求 xx）”。提示词正文及生成回执原样取自 response 文件。允许在代码块外写必要表头、问题、例外和变更摘要；这些说明不得混入可复制提示词。用户只要提示词时省略外部说明，内部检查不变。
`--report` 写到 `~/.aigc-video-gate/`（可用 `AIGC_GATE_DIR` 改）；报告里记 `created_at`，设了 `AIGC_SESSION_ID` 时还记会话标识，用来判断这份报告是不是本轮跑的。显示出来的交付行必须与本次放行报告成对一致（正文短哈希与需求短哈希同属一份报告），不手写。可选宿主钩子另见 `../../hooks/README.md`；本体流程与验收不依赖钩子。

## 证据边界

verify_delivery 会真实调用机械检查，并核对需求、正文、父稿、覆盖项、六域、素材读取声明、警告及独立复核是否匹配。它能拦截漏项、旧版本回执和未解决状态，不能证明填入的语义判断正确或读取声明真实。检查者必须实际看素材、判断镜头，行为测试必须检查真实产物和工具记录。

哈希只绑定版本，不是运行签名。Skill 文本本身不能禁止模型绕开工具；本工具只约束经其导出的已验收产物，不能声称宿主所有手工输出都已被拦截。每次付费生成仍受当次用户授权约束；文本验证不冒充成片成功。

## 本用户偏好的逐项执行记录

### 摄影（全套路径每次完整成稿必填）

review.json 增加 camera 数组，每个完整稿镜头一行，id 使用完整稿出现顺序，从1开始。即便只交付局部镜头，也核对合成完整稿各镜；无镜头标题的编辑命令使用 id=1。

```json
"camera": [
  {"id": 1, "mode": "moving", "quote": "摄影机缓慢向右横移", "effect_quote": "近处门框向左滑出，露出人物身后的窗沿", "reason": "说明本镜路线、实际幅度、时间与可读性相容"}
]
```

quote、effect_quote 必须准确存在于该镜正文，不能引用别镜来替代。缓推、横移等要有实际可见的尺度、位置、视差或显露关系变化；写了“运动”关键词或晃动衣服不代表摄影完成。短暂停稳用于关键读点可以，整镜固定须有明确来源。

固定只有两种来源，字段各不相同：

- **mode=fixed —— 用户明确要求固定**：用 source 保存用户原话的准确引文，quote 引用本镜固定摄影的正文原句，reason 写判断。用户确认了作者提出的固定建议时同样用 fixed，source 引用用户确认的那句原话。
- **mode=preserved —— 保留父稿或源视频的受保护摄影**：必须提供真实父稿（--baseline）或是编辑任务，同时引用 source 和正文。原素材明确规定摄影时也须说明用户将该维度锁定的依据，不能凭读到参考图就认定固定。

**作者自行固定（fixed_by_design）已撤销**，不再是合法 mode，verify_delivery 遇到它直接报错。如果某个具体条件确实使固定镜头更合适（本镜对白近景必须保口型同步、本镜在紧景别高速运动下主体结构会糊、本条产品微距的焦平面经不起机位移动），可说明理由并询问是否同意，问题写进表头“待你定”行；用户明确同意之前，当前交付仍采用符合要求的可见运动方案并记 mode=moving。普通产品、对白或微距题材本身不自动触发固定建议，也不因等待这项可选建议而停住成稿。用户同意后才改成 mode=fixed 并在 source 引用用户同意的原话。“不想设计运镜”“懒得想路线”“产品应该固定”仍然不是固定的理由，先补设计。

脚本拦截缺镜、缺本镜证据、无来源例外和已撤销的 fixed_by_design；真实幅度、来源是否构成明确摄影锁，仍由专业审查判断。不存在只凭字段填齐就证明运镜设计成立的保证。

### 多音字同音替换（实际替换时才填）

requirements.json 的 exact_locks 将完整原台词作为独立锁保留；包含台词的较大语段按本次授权分开记录非发音部分，不扩大替换。其他字段即使含相同字词也保持原锁。在 pronunciation 中记录完整原台词、实际发音台词、逐字改动。索引按原台词的 Unicode 字符从0开始；读音使用带声调数字的拼音（轻声5、ü写v）。这里只允许多音字在当前语境下同音同调的必要替换；没有替换可不填。

```json
"pronunciation_policy": "homophone_allowed",
"pronunciation": [
  {"original": "银行开门了。", "spoken": "银杭开门了。", "reason": "银行的行读hang2；杭同读hang2，只为确定发音",
   "replacements": [{"index": 1, "from": "行", "to": "杭", "source_pinyin": "hang2", "target_pinyin": "hang2"}]}
]
```

本用户已有一般授权，默认 homophone_allowed。当前明确字形不准替换时使用 exact_only 并保持原文；不能用一般偏好绕开当次明确要求。只替换实际发音文本，不替换屏幕文字、其他叙述、角色标识或素材名。没有发音歧义或读音不确定时不为“更稳”凑替换。

自审补充 `pronunciation_review: {"status":"pass", "entries_checked":1, "reason":"逐项说明语境读音、替换字读音同音同调，原意与说话人保持，其他字词标点和非发音字段不变", "unresolved":[]}`。机器核对位置、汉字、读音声明一致、改动穷尽和输出原句；不能认证填写的拼音正确，专业审查必须实际判断，不能编造读音通过。

先跑 check_prompt 时，将发音字段中实际采用的完整台词传给 --lock；原文与映射保存在 requirements 中，非发音锁照常原样传入。verify_delivery 会自行检查映射并从原锁计算实际发音锁，重新执行机械检查；无需伪造父稿或删除原始要求。任何发音映射变化都会改变需求哈希，必须重审。
